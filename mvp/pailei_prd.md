## 0. 项目元信息

| 字段 | 值 |
|---|---|
| 项目名 | Report Minner（包内代号 `pailei`，即"排雷"拼音） |
| 一句话目标 | 基于 A 股上市公司年报的「财务报告」章节，自动识别财报中可能的造假与风险信号 |
| MVP 范围 | 单家公司最近 3 年报的纵向排雷；不做行业对标、不做实时监控、不做投资建议 |

## 1. 项目背景与定位

### 1.1 行业现状与痛点

A 股上市公司年报常 200+ 页。专业投资者识别财报风险需要：

- 精读"第十节 财务报告"中的审计意见、三大报表、附注
- 对照历史趋势、同行业基线判断异常
- 交叉验证报表之间的勾稽关系

当前业内主要工具（同花顺 iFinD、Wind 风险模块、Choice 等）以"财务比率打分"为主，对**附注层面的"造假征兆"**（异常会计估计、关联交易、巨额商誉减值等）覆盖薄弱。开源社区也缺少聚焦"排雷"的可复用工具。

### 1.2 项目独立性

本项目是**完全自包含的独立项目**：

- 不依赖任何外部系统的运行时产物
- 不调用任何外部项目的 HTTP API
- 不假设用户已部署其他项目
- 不与其他项目共享数据库、配置、缓存

所有阶段（PDF 下载 → 解析 → 分析 → 报告）均在 Report Minner 进程内完成，数据全部落盘到本项目专属的数据目录。

### 1.3 项目定位

| 维度 | 说明 |
|---|---|
| 目标输出 | 财务风险排雷报告 |
| 关注点 | 造假征兆、风险信号 |
| 规则来源 | 领域硬编码规则 + LLM 附注阅读 |
| 目标读者 | 专业从业者（卖方/买方分析师、量化研究员、深度个人投资者） |

## 2. 目标用户与场景

### 2.1 目标用户

| 角色 | 占比预期 | 核心诉求 |
|---|---|---|
| 卖方/买方分析师 | 60% | 在写报告前快速做"排雷清单"，识别潜在雷点 |
| 量化研究员 | 25% | 将排雷结果作为另类因子/过滤信号 |
| 个人深度投资者 | 15% | 自定义标的的深度尽调 |

### 2.2 核心场景

**场景 1：分析师尽调**
分析师需要对一家公司做深度分析前，先跑一次排雷：
1. 输入公司名（如「宁德时代」）+ 年份（如 2023/2024/2025）
2. 系统自动获取年报 → 解析 → 排雷
3. 系统输出排雷报告（Markdown + JSON）
4. 分析师阅读报告，结合自身判断决定是否继续深度分析

**场景 2：批量预筛（V2 扩展，MVP 仅 CLI）**
研究员需对持仓/候选池做批量预筛：
1. 输入一篮子股票代码
2. 系统逐家排雷，输出汇总的"雷点清单"

**场景 3：纵向对比**
对同一公司连续多年排雷，观察"雷点"是否新增/消失：
1. 多次扫描同一公司
2. 系统自动保留历史 JSON，可对比 trend

## 3. 核心流程（6 阶段）

完整流水线按时间顺序，全部在 Report Minner 进程内完成：

```
┌─────────┐  ┌─────────┐  ┌─────────┐  ┌─────────┐  ┌─────────┐  ┌─────────┐
│ 1.获取   │→ │ 2.解析   │→ │ 3.初分   │→ │ 4.深分   │→ │ 5.清单   │→ │ 6.报告   │
│ PDF     │  │ PDF→MD  │  │ 三表扫描  │  │ 附注检索  │  │ 审核汇总  │  │ JSON+MD  │
└─────────┘  └─────────┘  └─────────┘  └─────────┘  └─────────┘  └─────────┘
```

### 3.1 阶段 1：获取年报 PDF

两种入口（用户在 CLI 中二选一）：

**入口 A：在线下载（自动）**
- 系统自动访问深交所/上交所公开披露页面
- 支持深交所（000/001/002/003/300 前缀）和上交所（600/601/603/605/688 前缀）
- 自动处理页面挑战与下载 PDF
- 落盘到本项目的数据目录；计算 SHA-256 用于去重

**入口 B：用户上传（手动）**
- 用户通过 CLI 提供本地 PDF 路径
- 落盘到相同的数据目录

**默认下载范围**：最近 3 年（用户在 CLI 中可指定）。

### 3.2 阶段 2：解析 PDF → MD（财务报告子章节切分）

**核心动作**：

1. **PDF 切分**：识别"第十节 财务报告"起始页，拆为业务报告 PDF 与财务报告 PDF
2. **MD 解析**：对财务报告 PDF 调用 PDF→MD 服务（OCR 引擎），输出 Markdown
3. **子章节切分**：识别 11 类一级章节（详见附录 A），输出独立的子章节文件
4. **标题/子标题提取**：构建导航索引（每个章节的起止行号、子节列表），便于后续精确定位
5. **三表抽取**：从"二、财务报表"中识别并解析合并 + 母公司的资产负债表/利润表/现金流量表/所有者权益变动表（共 8 张），输出结构化数据

**容错策略**：
- 一级章节识别：依次尝试精确正则、模糊正则、TOC 反查
- 章节不完整：记录到缺失清单，继续后续阶段（缺失章节对应的规则标记为"未审查"）
- 表格识别失败：保留原始 MD 文本，回退到上下文估算或交人工

### 3.3 阶段 3：初步分析（合并口径三大表规则化扫描）

**核心动作**：基于附录 B 的 5 大类规则（~20 项），对每张报表、每个科目执行规则扫描。每条规则返回 0 或 N 个 Finding（命中点）。

**规则引擎核心概念**：
- 一条规则 = 一个独立可测试的判断逻辑（如"账面巨额现金 + 高额短期借款"）
- 规则接收财务数据快照，输出命中的 finding（含科目、年份、严重度、证据）
- 规则按类别组织：审计 / 资产负债表 / 利润表 / 现金流量表 / 公司治理

### 3.4 阶段 4：深度分析（基于问题科目的附注检索 + LLM 阅读）

**核心动作**（仅对 MEDIUM/HIGH 级别 finding 执行）：

1. **附注定位**：根据 finding 中的科目（如"应收账款"），在「七、合并财务报表项目注释」中找到对应附注子节
2. **附注文本提取**：读取附注 MD 原文（含期初/期末对比、账龄结构、坏账计提等明细）
3. **LLM 阅读**：
   - 输入：附注原文 + finding 上下文 + 提示词（"请评估上述附注是否能合理解释该异常点"）
   - 输出：判定（确属异常 / 可解释 / 信息不足）+ 引用证据 + 严重度调整建议

**LLM 调用控制**：
- 每家公司最多 20 次调用（按 finding 数量）
- 每次调用附注上下文限制在 8K tokens 以内
- 超时 60s，失败则保留初分结果并标记为 skipped

### 3.5 阶段 5：审查清单（汇总去重 + 严重度排序）

**核心动作**：
1. 去重（同 rule + 同科目 + 同年份合并）
2. 严重度排序（HIGH > MEDIUM > LOW）
3. 按附录 B 的 5 大类分组
4. 标记每条的 deep_status（confirmed / explained / skipped / not_run）

### 3.6 阶段 6：生成报告（JSON + Markdown）

**核心动作**：
1. 渲染 JSON：按统一 Schema 输出（结构化、可机读）
2. 渲染 Markdown：使用报告模板，包含：
   - 概览（公司、年份、风险评分、雷点数量）
   - 按 5 大类分组的 findings 表格
   - 每个 finding 的详细说明（规则名、触发条件、附注引用、LLM 判定）
   - 附录：原始数据快照

## 4. 附录 A — 财务报告章节结构

源自用户口述，2 层精度，**章节顺序相对固定但可能出现额外节**：

```
第十节 财务报告
├── 一、审计报告                          [01]
├── 二、财务报表                          [02]
│   ├── 1. 合并资产负债表
│   ├── 2. 母公司资产负债表
│   ├── 3. 合并利润表
│   ├── 4. 母公司利润表
│   ├── 5. 合并现金流量表
│   ├── 6. 母公司现金流量表
│   ├── 7. 合并所有者权益变动表
│   └── 8. 母公司所有者权益变动表
├── 三、公司基本情况                       [03]
├── 四、财务报表的编制基础                  [04]
├── 五、重要会计政策及会计估计               [05]
│   └── （多个子项，说明各科目会计准则）
├── 六、税项                              [06]
│   └── （各子公司税收政策，是否有税收优惠）
├── 七、合并财务报表项目注释                [07]
│   └── （N 个子项，对合并报表中每个科目的详细分析）
├── 八、研发支出                           [08]
├── 九、关联方及关联交易                    [09]
├── 十、股份支付                           [10]
└── 十一、母公司财务报表项目注释             [11]
```

**说明**：
- "可能不止这些章节，但包含这些章节" — 实际年报常有补充节（如「十二、其他重要事项」「十三、补充资料」），识别器需支持扩展
- 索引 `[NN]` 作为输出文件名前缀，便于排序

## 6. 功能模块概述

按职责划分（具体实现留给架构设计）：

### 6.1 PDF 获取模块
- **在线下载**：支持深交所/上交所；处理页面挑战与去重
- **手动上传**：CLI 接收本地 PDF 路径

### 6.2 PDF 解析模块
包含 4 个子能力：
- **PDF 切分**：业务/财务拆开
- **PDF→MD**：OCR 引擎统一封装（MinerU / DeepSeek OCR 等）
- **子章节切分**：财务报告子章节识别 + 标题导航
- **表格抽取**：三表 HTML 表格 → 结构化数据

### 6.3 规则引擎模块
- **规则抽象**：每条规则是独立可测试的判断逻辑
- **执行器**：批量执行所有规则，输出 findings
- **规则清单**：见 §5

### 6.4 附注检索模块
- 输入：finding 指向的科目（如"应收账款"）
- 输出：附注原文

### 6.5 LLM 阅读模块
- 输入：finding + 附注原文 + 提示词
- 输出：判定 + 严重度调整建议
- 失败降级：单条调用失败不影响整体

### 6.6 审查清单模块
- 输入：初分 + 深分 findings
- 输出：去重排序后的清单

### 6.7 报告输出模块
- 输入：findings + 导航索引
- 输出：JSON（结构化）+ Markdown（人类可读）

### 6.8 CLI 入口
提供子命令覆盖 6 阶段，支持：
- 完整流程一键跑
- 单阶段调试
- 单规则验证
- 配置文件覆盖

## 7. 数据流转（不涉及技术实现）

### 7.1 输入
- 年报 PDF（在线下载 / 用户上传）
- 公司名、年份列表

### 7.2 中间产物
- 切分后的业务/财务 PDF
- 财务报告 MD（OCR 输出）
- 财务报告子章节 MD + 导航索引
- 三大报表结构化数据（JSON）

### 7.3 输出
- 排雷报告（JSON）：结构化、可机读、可接入其他系统
- 排雷报告（Markdown）：人类可读、可打印

**数据流原则**：
- 所有中间产物落盘，便于断点续跑
- 同一份输入 → 同一份 JSON（除时间戳、UUID）
- 每个 finding 必须有证据引用（章节 + 数值快照 + 行号）

## 8. 非功能需求

| 维度 | 要求 |
|---|---|
| **性能** | 单家公司 3 年报 端到端 < 10 分钟（含 PDF 下载、解析、LLM 调用） |
| **可重复** | 同一份输入 → 同一份 JSON（除 `generated_at`、`finding_id`） |
| **可解释** | 每个 finding 必须有 `evidence` 字段（含 section_ref + 数值快照 + line_range） |
| **原子性** | 各阶段中间产物全部落盘，便于断点续跑 |
| **错误隔离** | 单条规则失败不影响其他规则；单条 LLM 调用失败降级 |
| **语言** | CLI 日志中文；报告正文中文 |
| **隐私** | PDF/解析产物仅落盘到本地；LLM 调用需明示（用户可选择跳过深度分析） |
| **离线可用** | 已有 PDF + MD 的情况下，断网可完成分析阶段（除 LLM 调用） |

## 9. 范围边界

### 9.1 MVP 不做（明确排除）

- ❌ 投资建议、买卖信号
- ❌ 行业对标（"高于同行""低于同行"）
- ❌ 实时监控、定时任务
- ❌ 自动下单、API 接入券商
- ❌ 多语言（仅中文）
- ❌ Web UI（仅 CLI）

### 9.2 V2 路线（不在本期 spec）

- 🔜 同业对标（**用户明确：后期通过分析同业年报的数据来实现**）
- 🔜 公告/问询函接入（用于 5.5 公司治理 + 5.2 关联方判断）
- 🔜 行业基线（用于毛利率分位等规则）
- 🔜 Web UI
- 🔜 批量预筛（一篮子股票）
- 🔜 历史 trend 对比（同一公司多次扫描的对比）
- 🔜 排雷规则的机器学习调优（基于历史造假案例）
